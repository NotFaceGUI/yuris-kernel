## 3. P0 阻塞项(按启动顺序)

### P0-1 `_STR`(系统变量 id 52)语义缺失 → 宏任务 Fatal

**现象**(headless 1500 帧,聚合日志):

```text
266 × Unimplemented rt.sysvar.unimplemented  _STR
   at es_scenario_load.yst pc17/18/19/26
   at es_scenario_macro_変数n.yst pc22/23
1 × Fatal rt.var.undeclared  @3165
   at es_scenario_macro_変数n.yst pc24
```

**根因链**:

1. `es_scenario_macro_変数n.yst pc22` 是
   `INT @3165 = int($_STR(@3060, 0))`(实测窗口:
   `v($#52) v(@3060) 0x2c i0 at[] cast_int`);
2. `_STR` 在 ycd/ysv 里有声明(`id=52, ty=3, dims=[1]`),但**没有手册页**,
   内核落入 `undoc()` → `Unimplemented`,该 `INT` 命令按"无副作用"跳过;
3. `pc24` 立刻 `LET @1168[@3165] = @3166`,读未声明变量 → **Fatal**,
   宏任务终止 ⇒ 标题宏链断掉。

**要补什么**:

- 用 v555 官方 exe RE `_STR` 的 getter(0.495 的 sysvar 分派在 `0x446b93`
  族;v555 地址待定),钉死:
  - `$_STR(a, b)` 的两个下标分别是什么(从脚本用法看是
    `(宏帧号, 参数号)`,但**未取证**);
  - 写入侧:宏参数是谁写进 `_STR` 的(`es.ScenarioMacro.SetParam`?);
  - 与 `_PSTR` 的区别(`_PSTR` 是 GOSUB 参数,`_STR` 不是)。
- 在拿到 RE 前,不要用"返回空串"蒙混:那会让 `INT` 成功、`@3165=0`,
  后续宏参数全 0,行为不可信。

**判定标准**:同一 1500 帧运行中 `rt.sysvar.unimplemented _STR` 归零,
`@3165` Fatal 消失,宏任务继续执行到 `es.ScenarioMacro.CSEL/TITLE` 之后。

### P0-2 GAMEMain UI 按钮纹理状态机没接上(画面黑的主因候选)

**现象**:

| 诊断 | 次数(1500 帧) | 内容 |
|---|---:|---|
| `gfx.info.missing` | 101,416 | `CGINFO[LINT2]` 目标 `:/W0/ES.GAMEMAIN.*.BT.OFF=0=1` 不存在 |
| `gfx.info.unsupported` | 31,405 | `CGINFO[LINT2] 需要像素/未分类语义,未取证` |
| `gfx.layer.missing` | 2 | `CGACT: 图像加工源 :/W0/.BT.OFF1 不存在` |

**关键事实**:

- 屏幕 pass 里的按钮层纹理是**基名**(如
  `cgsys_cn/main/button/btn_voice`),而包里实际资产是
  `btn_voice_off/_on/_over/_na.png`(已用包遍历确认);
- 按钮状态 `BT.OFF=0=1` 需要由 `CGACT/COPY2` 从 `_off/_on/...`
  组合出快照,当前 `CGACT` 的源 `:/W0/.BT.OFF1` 不存在(组名中间段为空),
  说明 **BT 组/临时层的命名或创建顺序**与官方不一致;
- 大量 `CGINFO[LINT2]` 是按钮搜索对"可选弹出层"的探测,missing 本身可能
  正常,但 31,405 条 `unsupported` 里是否有按钮布局必需的查询**未分类**。

**要补什么**:

1. 把 `CGINFO[LINT2]` 的语义按官方处理体补齐(至少区分"层不存在"与
   "查询项未实现",前者应返回官方同值的 0/-1 而不是 Unimplemented 噪声);
2. 追 `:/W0/.BT.OFF1` 组名为空:在 `es_button*.yst` 里打印
   `BT` 组名来源变量,和官方 trace 对拍;这是按钮快照建不出来的直接原因;
3. 资产基名 → `_off/_on/_over/_na` 的后缀选择规则:确认是 `CGACT`/
   `COPY2` 组合还是 `BT` 状态机在 `CG` 时刻选后缀;当前直接拿基名去
   `TextureStore` 会 MISS(已实测 `btn_voice` MISS、`tip_meswindow.png`
   只有 154 B 占位);
4. 修好后用 `display JSON` 检查按钮层的 `texture.kind` 应为
   `snapshot` 或有效 `asset`,不能是缺省基名。

**判定标准**:GAMEMain 画面出现按钮/消息窗(不再纯黑);
`CGACT: :/W0/.BT.OFF1 不存在` 归零或只剩已证实的可选路径。

### P0-3 屏幕过渡/`SPL101` 把整屏刷成黑(from/to = solid black)

**现象**(display JSON,screen pass 第 1 个 op):

```json
{"op":"transition","tid":":/W0/SPLTR101","fade":0.75,
 "from":{"kind":"solid_black_1x1"},"to":{"kind":"solid_black_1x1"},
 "layer":{"id":":/W0/SPL101","alpha":256,...}}
```

**含义**:过渡的两端纹理都没解析出来,渲染器退化成 1×1 黑;
`SPL101` 的 `from/to` 本应是**前后屏幕快照**(官方 `YS_Texture1/2`),
现在成了黑,整屏被覆盖。

**要补什么**:

- 查 `GfxState::op_for_layer` 的 `transition_pair` / `transition_mask_base`
  在 `SPL101` 上的解析:配对层 `SPLTR101` 是否存在、是否被
  `CGACT[SIZE/REVERSE]` 做进表面;
- 若配对层是"组",确认 `group_has_visible_content` 的判定;
- 屏幕前后快照的捕获时序:`from` 应是当前屏幕,`to` 应是目标屏幕;
  目前两端都落到 `SolidBlack1x1` 说明捕获路径没接上(和 `capture.rs`
  的 `replay_snapshot` 不是同一条;display 过渡走 gfx 状态)。

**判定标准**:`transition` 的 `from/to` 至少一端是
`{"kind":"snapshot"}` 或有效资产;logo 结束后的淡入不再黑屏。

### P0-4 背景 CG 没建出来(`CG` 无 FILE/RID + 目标层不存在)

**现象**:

```text
Verbose  s190 pc6   CG: CG 无 FILE/RID 且目标层不存在:官方返回 -1,不建节点
Verbose  s183 pc169 CG: 同上 ×2
```

screen pass 里没有背景层,只有 UI 按钮/消息窗。标题/场景背景应在
`CG[ID=..., FILE=...]` 时建层;现在这些"只给 ID 的激活"找不到目标层,
说明**前一条建层命令没成功**(或层键规范化不一致)。

**要补什么**:给 `CG` 的 `layer.missing` 诊断补上 `ID` 原值,
按脚本顺序找到第一次建该层的命令,确认是 `FILE` 解析失败、资产缺失,
还是 `ID.N/IDNO` 键拼接与后续引用不一致。

**判定标准**:标题场景有背景层进入 screen pass(非黑)。

## 7. 建议顺序(最短路径)

1. **P0-1 `_STR`**(RE v555 getter + 写入侧):消掉宏 Fatal。
2. **P0-3 过渡黑屏**:先让画面不再被 `SPL101` 全黑覆盖(哪怕只显示

   让 GAMEMain/标题按钮出现。
4. **P0-4 背景 CG**:标题背景进入 screen pass。
5. 之后才是 P1(CGINFO 分支、声音 SYSSE、PRODUCT 其余 COM、
   `MEM=99999`)与正文文本逐字对拍。

- 启动后可见**品牌 logo → 标题画面**(与官方同序,截图可对照);
- 标题 START 后进入正文,消息窗有字、翻页/点击推进;
- 存档/读档(MEM 与 FILE 各一次)后场景与变量恢复;

## 9. 跨版本隔离(不破坏老模块)

v555 的适配**不靠散落的 `if version == 555`**,分两类处理:

### 9.1 参数形状不同 → 按参数名/形状分派(已有)

| 命令 | 0.495 形状 | v555 形状 | 判据 |
|---|---|---|---|
| `TEXT` | `ID/OUTPUTMODE/…` | `FILE/LET/CLEAR` | 是否存在 `FILE` 参数 |
| `SAVE`/`LOAD` | `FILE/DNO/SET…` | 多 `MEM` | 是否存在 `MEM` 参数 |
| `PRODUCT` | **0.495 ysc 无此命令** | `COM/LET/PINT…/PSTR…` | 命令是否存在 + 参数形状 |

这些分支对老工程天然不可达,不需要版本判断。

### 9.2 同名同参数、语义随引擎版本不同 → 单一工程档案

目前只有 `VARINFO[SJISCODE]`:

- 0.495 官方处理体零引用(无操作);
- v555 处理体 `0x4554a9` 计算首字符码;
- 两边 ysc 参数表完全相同(都有 `SJISCODE` 槽)。

处理:用工程自带 `ysc.ybn` 头的**目标引擎版本**做一次判定
(`ysc 495` → 惰性槽;`ysc 555` → 计算),判定集中在
`op_varinfo` 一处并留 `aligned-stub` 取证,不散落到其它 handler。
回归:

```text
fixture::varinfo_sjiscode_returns_first_char_code   (ysc=555,计算)
fixture::varinfo_sjiscode_is_inert_on_495_projects (ysc=495,无操作)
```

### 9.3 与版本无关的正确性修复

`GOSUB/RETURN` 三组参数拆分是**全版本正确性修复**(手册 + 引擎三组数组),
不是 v555 特例;0.495/0.479 旧用例全绿,说明没有依赖旧 bug 的行为。

### 9.4 老模块回归基线(本轮实测)

- `cargo test -p yu-rt`:122 lib + 4 + 11 + 4 + 3 + 136 + 3,全过
  (含 0.495 ERIS 语料一致性、600 帧普查、v494/v481/v486 ABI 用例);
- `cargo test -p yu-save`:23 通过(含官方 seld/缩略图 golden);
- 0.495 ERIS 136 个脚本扫描:`VARINFO` 实际只用了
  `DIMSIZE/LENGTH/NO/SEARCH/STR/STRTYPE`,**SJISCODE 0 次** ——
  即使不加版本门,也没有老语料会走到新分支;加门是为了守住"未来老工程"。
