# YPF 封包格式(官方 YSPac 0.495 实测)

> 证据: `workbench/project-eris/data.ypf`(官方 YSPac 0.495 产出,1407 条目,31,501,753 字节)
> 逐字节解析 + 引擎加载器反编译(`yu-ris.exe` sha256 `4f5eefa3…`:`FUN_0045e3b8` 建表 /
> `FUN_0045eda0` 目录扫描 / 读序见 §5)。旧接手线 `yuris-format/src/ypf.rs` 的 `LenEncNot`
> 解析器**字段切分与索引起点与官方包不符**(见 §6),以本文为准。

## 1. 头部(32 字节)

```
+0x00  char[4]  "YPF\0"
+0x04  u32      版本(官方 0.495 为 495;引擎接受 ==495 或 >=234)
+0x08  u32      条目数
+0x0C  u32      数据区起始偏移 = 索引区结束位置(从文件头算起)
+0x10  u8[16]   保留(全零;官方 YSPac 输出如此)
```

**索引区从 0x20 开始**,到 `+0x0C` 的值结束。注意:v494 等更早的包文件头可能为 0x24
(旧接手线按 0x24 实现,在其测试包上自洽)——读取器必须**探测起点**:
对候选起点(0x20/0x24)按条目规则行走,选"恰好走到数据区起点"的那个。

### 1.1 索引方言(必须先判方言,再谈字段)

旧接手线的实现里记录了两族并存,本仓库**当前只实现并验证了其中一族**:

| 方言 | 名字长度 | 名字编码 | 步长 | 本仓库状态 |
|---|---|---|---|---|
| **LenEncNot**(本 demo 包 = 官方 YSPac 0.495 产出) | 显式 `u8 lenEnc`,`nameLen=T[(0xFF-lenEnc)&0xFF]` | 逐字节取反 `~b` | `nameLen+27` | **已实证**(本文 §2/§3;1407/1407) |
| **NulXor**(部分更早/其他发行包) | `NUL` 结尾,步长按名字实际长度 | 逐字节 `XOR key`(逐游戏不同;旧线观察到 `0xC9`/`0xFF`) | `nameLen+26` | **未验证**;遇包即显式报"未验证方言"并挂 DIV-002,**禁止猜测 key** |

> 本次 A 的重启范围: **只做 LenEncNot**,语料 = `workbench/project-eris/data.ypf`。
> NulXor 在拿到真实样本与官方对照之前不实现(旧线 DIV-002 保持 open)。

## 2. 索引条目(步长 = nameLen + 27)

```
+0x00  u32   hash           MurmurHash2(名字字节, seed=0)   ← 与存储哈希逐条实证一致
+0x04  u8    lenEnc         nameLen = T[(0xFF - lenEnc) & 0xFF]
+0x05  u8[nameLen] name     名字字节逐字节取反(~b);路径用反斜杠、小写
+...   u8    flag           0 = 负载为 zlib 流;2 = 负载原样存储(实测)
+...   u32   usize          解压后大小
+...   u32   csize          ���储大小
+...   u8    unknown0       恒 0(语义未定,勿猜)
+...   u32   dataOffset     负载在文件内的绝对偏移(压缩流或裸数据的首字节)
+...   u32   unknown1       恒 0(未定)
+...   u32   unknown2       非零(疑似校验值;未验证出算法,勿依赖)
```

- 长度解码表 `T` = 恒等表 + 12 对交换:
  `(3,0x48) (6,0x35) (9,0x0B) (0x0C,0x10) (0x0D,0x13) (0x11,0x19)
   (0x15,0x1B) (0x1C,0x1E) (0x20,0x23) (0x26,0x29) (0x2C,0x2F) (0x2E,0x32)`。
- **没有单独的"数据记录头"**:`dataOffset` 直接指向负载首字节
  (flag=0 时首字节应为 `78 01/9C/DA`;flag=2 时即原始文件内容,如 PNG 的 `89 50 4E 47`)。

## 3. 条目示例(实测)

| 名字 | flag | usize | csize | dataOffset | 负载首字节 |
|---|---|---|---|---|---|
| `ysbin\yst00034.ybn` | 0 | 1,525,761 | 497,152 | 0x31B36B | `78 da`(zlib) |
| `cgsys\saveload\btn_page08_over.png` | 2 | 214,784 | 214,784 | 0x11001A4 | `89 50 4E 47`(PNG) |
| `cgsys\main\texticon_over\icon_04.png` | 2 | 44,288 | 44,288 | 0x1C81812 | `89 50 4E 47` |

hash 校验:MurmurHash2(name, seed 0) 与索引存储哈希**逐条相等**(抽验 4/4)。

## 4. 引擎侧行为(反编译实证)

- 包发现(`FUN_0045eda0`):从根目录 `FindFirstFileA("*.*")` 递归;子目录**只递归名为
  `pac` 的目录**(白名单就这一个);文件后缀 `.ypf` → 非 `update1..9.ypf` 者作为
  **基础包**逐个挂载,`updateN.ypf` 按 N 登记为增量层(后挂覆盖)。
- `DAT_008015b4 != 0` 时走单包挂载分支(`FUN_0045ea8c`),不扫描目录 ——
  发布模式(`SYSTEMMODE[DEBUGMODE=0]`)属于此路径。
- 挂载后引擎按**项目目录相对**路径查找(`ysbin\yst%05d.ybn` 等);
  因此包内路径**不能带 `data\` 前缀**(这是 YSPac 拖"文件夹"与拖"文件夹内容"的差别)。

## 5. 打包流程(官方 YSPac 的正确姿势)

1. 打开 `YSPac.exe`;
2. 在资源管理器里进入**项目目录(`data/`)**,`Ctrl+A` 全选其**内容**(各子目录),`Ctrl+C`;
3. 回 YSPac `Ctrl+V`(列表出现 11 个顶层目录);
4. `ファイル` → `全ファイル圧縮(A)...` → 指定输出(如 `data.ypf`);
5. 把 `data.ypf` 放到**游戏根目录**(与 `yu-ris.exe` 同级);
6. `data/config/projectconfig.txt` 设 `SYSTEMMODE[DEBUGMODE=0]`(发布模式)→
   引擎直接读包内 ysbin,不再编译(实测出标题画面)。

## 6. 已知坑与勘误(留痕)

1. **索引起点**:官方 0.495 包为 0x20;旧接手线按 0x24 实现(其测试包自洽)——
   读取器需按"行走恰好抵达数据区起点"来判定。
2. **字段切分**:旧接手线 `LenEncNot` 用 `code + NUL + usize + csize + off + zero4 + tail8`;
   实测为 `flag + usize + csize + pad1 + off + unk + unk`(Tyn 的 NUL 容忍掩盖了整体偏 1 字节)。
   症状:usize/csize 看似"差不多"但偏移全错,读取大包时读出垃圾——即接手线 DIV-001。
3. **flag 语义**:0 = zlib,2 = 原样(不是笔记写的 0/1)。
4. **未知字段**:索引尾 8 字节(其中后 4 字节非零)与 `unknown0` 语义未验证;
   引擎读取路径不依赖它们,打包时按官方包形状填(0/0/原值)并保留不解释。
