# DIV-GFX-064 · `CG`/`CGACT` 浮点坐标的规约点(亚像素 vs 取整)

- 状态:**fixed(no-manual)**(种类 2 的序言与消费点已由 REA 定案;具体 f64→i64
  指令未定位,但可观测位置连续性已由语料自证 + 实机 trace 对齐;内核保留 f64 到顶点)
- 取证对象:官方 `0.495` `yu-ris.exe`(`CG` 处理体 `FUN_0042f809`),
  语料 `ERIS/Sprite/es_Sprite.yst`

## 1. 现象

脚本把**浮点**位置喂给 `CG`/`CGACT`:

```text
es_Sprite.yst:8574   FLT[@LEFT_X = ...]              // MATH3D 输出,浮点
es_Sprite.yst:8703   CG[ID=$dst X=@LEFT_X Y=@LEFT_Y]
es_Sprite.yst:8538   CGACT[ID=$src ID2=$dst SIZE2=1
                       FX=@X1*100+@FLX FY=@Y1*100+@FLY
                       FX2=@X2*100+@FLX FY2=@Y2*100+@FLY
                       FSX=@SIZE_X*100 FSY=@SIZE_Y*100]
```

脚本注释原文(`es_Sprite.yst` 的 `es.CGACT_SIZE` 附近):

> 表示位置 @LEFT_X,@LEFT_Y の小数点値を掃い、それを CGACT[SIZE2=1 ～] に伝える

即:**整数部分走 `X`,`小数部分 ×100` 走 `FX`**。`FX/100` 就是真实的亚像素
位置,分辨率 0.01px(实测序列 `-0.49 → -0.48 → …`)。

## 2. 两层证据的张力

### ① 消费点按 64 位整数读(REA,确定)

`FUN_0042f809` 的 X/Y 读取块,`0x42b064` / `0x42b09d` 起:

- `MOV reg, dword ptr [idx*8 + 0x683740]` —— 取参数槽低 32 位;
- `OR reg, [idx*8 + 0x683744]` —— 合并高位做零判定。

⇒ **消费点是 64 位整数语义,不读类型标记,没有 ftol/取整。**

### ② 官方渲染位置正确(语料自证,确定)

`es_Sprite.yst` 是官方 SDK 编译产物,大量使用上述浮点形式,官方引擎在
β4 演出里位置连续、无阶梯。

⇒ 规约必然发生在**求值阶段**(参数写进 `0x683740` 之前),而不在消费点。
参数序言 `FUN_00429fd1`(`0x429fd1`)把实参求值成「64 位值 + 一字节类型
标记」,但**把 f64 变成 i64 的具体指令尚未定位**。

## 3. 内核的裁定

**保留 f64 一路到后端 `float` 顶点**(与官方 D3D9 顶点阶段同类型),
理由:

1. 可观测行为(位置连续性)与官方一致 —— 这是唯一真值口径;
2. 消费点读 i64 是**实现细节**,照抄它会把 0.3px/帧 的位移量化成
   「一帧不动、下一帧跳 1px」的阶梯(2026-10-26 实机 + 逐帧 trace 确认:
   `X=260.71190987262014 → 261.79777521694757`,每帧 1.08px)。

落地位置:

| 层 | 改动 |
|---|---|
| `yu-gfx` `Transform.x/y` | `i64` → `f64` |
| `yu-gfx` `ImageOp.x/y/x2/y2` | `Option<i64>` → `Option<f64>` |
| `CG[X/Y]` 读取 | `as_int`(遇小数整条丢) → `as_f64` |
| `CGACT` 区域 `FX/FY/FX2/FY2` | `(v/100).round() as i64` → `v/100`(浮点) |
| wgpu 后端 | 顶点 `f64` → `f32`;`CGACT` 区域 → UV 子矩形(亚像素采样) |
| soft 后端 | `draw_image` 位置 `f64`;新增 `sample_subpixel`(D3D9 texel 中心口径) |

**仍取整的槽**(语义上确实是整数像素,有意保留):

- `CG[Z]` —— 层排序键;
- `CG[SX/SY]` —— 纹理尺寸;
- `COPY` 区域、`RECTPAINT`/`RESIZE` 区域、`CGACT[TEXT]` 字符落位。

## 4. 参数种类 2(`X+=`)的算术语义 —— **已定案:不是累加**

REA `FUN_00429fd1`(参数序言,包内 `0x429fd1`)按「参数类型字节」分派,
三路互斥:

```c
cVar1 = *(char *)(param_name + kind_table[command]);   // 类型字节
if (cVar1 == 0) {            // 0 = 数字表达式
    lVar13 = (DAT_008018b4[subtype])(script_base + off, len);   // 求值
    *(int *)(&DAT_00683740 + i*8) = (int)lVar13;   // 参数值槽 lo
    *(int *)(&DAT_00683744 + i*8) = hi;
    // 引用三表 0x683a60 / 0x683c00 / 0x683da0 ← 全局临时(DAT_007b4160/68/4171)
} else if (cVar1 == 1) {   // 1 = 字符串 → malloc(0x1000) + 拷贝
    ...
} else if (cVar1 == 2) {   // 2 = **脚本内偏移**
    *(int *)(&DAT_00683e20 + i*4) = script_base + off;
    // 参数值槽 0x683740/0x683744 **一个字都不写**
}
```

**结论**:种类 2 不做任何算术,也不产生数值;它只把「脚本体内的偏移」登记到
独立表 `0x683e20[i]`,供消费点按偏移直接取内联数据。因此:

- **不可能是「在当前值上累加」** —— 参数序言里没有任何读旧值的路径;
- 也不是普通数值 —— 数值槽不被写。

内核据此按「普通数值(赋值)」处理:VM 已把载荷求值成 `Value`,消费点直接
赋值(与种类 0 同口径)。这与实机现象一致 —— 若按累加处理,`es_Sprite.yst`
每帧的 `CG[…] X+=(@es.GSX/2)-(@WSX/2)` 会让持久层逐帧漂移、补间结束时
"跳回原位"(2026-10-26 实测)。

`ArgValue::offset` 字段因此**降级为诊断信息**,不参与运算。

**消费点证据(REA,`0x42c9a7`,CG 族处理体内)**:

```asm
MOV EDX, dword ptr [EAX*0x4 + 0x683e20]   ; 取偏移表[i](= script_base+off)
MOV dword ptr [ESP + 0x58], EDX           ; 存进本帧参数结构
```

消费点把 `0x683e20[i]` 当**脚本体指针**保存(后续按该指针读内联数据),
既不当数值、也不做累加。全文件共 6 处引用
(`0x42c9a7/0x42c9c5/0x445b33/0x448326/0x448335/0x44c277`),同属这一形态。

内核差异(记录在案,不属行为分歧):官方按「脚本体内联数据指针」取值,
内核走 VM 表达式求值。对本作语料,两者产出的数值一致(实机逐帧比对)。

## 5. 其他关联

- **官方把 f64 规约成 i64 的指令未定位**(需要官方引擎 trace,或继续追
  `FUN_00429fd1` 的 `DAT_008018b4[subtype]` 求值器家族)。
- **`HORIZONTAL/VERTICAL` 改为 UV 负步长**、`SIZE` 改为 UV 子矩形后,
  soft 与 wgpu 不再逐位相同。soft 是自建参考实现(真值 = SDK demo),
  该对比门禁已按主人指示默认关闭(`EngineOptions::reconcile = false`)。

## 6. 勘误(2026-10-27):参数种类 2 = **增量**,不是赋值

§4 由「序言不写数值槽」推出「不可能是累加」,该推理**不成立**,本轮以实机
行为与窗口编码为准推翻:

**证据 A(窗口记录编码,RSX 窗口 12 字节)**

```text
{ u8 kind, u8 flag, u16 slot, u32 length, u32 offset }
```

`slot` 的**高字节**就是官方参数类型字节:

| 脚本文本 | `slot` | 类型 |
|---|---|---|
| `CG[… X=…]` | `0x0001` | 种类 0(普通值) |
| `CG[… X+=…]` | `0x0101` | 种类 2(增量) |

**证据 B(行为)**:上一轮内核把 `offset` 恒判 false(用 `w.rec.kind` 当种类码
比对,那是槽号不是种类码),`es_Sprite.yst:8173` 的
`CG[ID=$L1 X+=(@es.GSX/2)-(@WSX/2)]` 在补偿量为 0 时把 `x` 赋成 0 ⇒
立绘钉在屏幕最左(用户报的第一个症状)。改为 `w.rec.slot & 0xff00 != 0`
判定、按 `当前值 + v` 运算后,位置序列收敛在 `240.93` 并保持稳定,补间
结束不漂移。

**为何与 §4 不矛盾**:序言(`FUN_00429fd1`)对种类 2 只是**登记偏移**、
不写数值槽 —— 这点没错;错的是由此推断消费点不做算术。消费点
(`0x42c9a7` 等 6 处)把 `0x683e20[i]` 取进本帧参数结构,层的属性应用路径
再按类型字节决定「赋值 / 叠加」。序言不写槽 ≠ 语义不是增量。

**结论(现行)**:`X+=`/`Y+=`/`Z+=`/`A+=` 一律按增量处理,回归见
`crates/yu-gfx/tests/parity_fixes.rs::cg_numeric_offset_params_accumulate`。

## 7. `es.CGACT_SIZE` 的 `FX/FY` 是**位置量化补偿**,不是源坐标

`es_Sprite.yst` 的 `es.CGACT_SIZE` 只发定点键(中等质量分支):

```text
FX = @X1*100 + @FLX        @FLX = -(@LEFT_X*100 % 100)
```

脚本注释写明 `@FLX` 的作用是「@LEFT_X 的小数点値を掃い」。因此

```text
FX/100 = X1 - frac(LEFT_X)       真实源起点 = LEFT_X + FX/100
```

直接当源坐标会让 UV 窗口整体偏移 `frac(LEFT_X)` 且**逐帧变化** —— 采样窗口
在纹理上来回滑动,表现为立绘边缘一帧一像素地抖。

内核:`ImageOp.region_from_fixed` 标记定点键;输出(`state::frame()`)时按目标
层当时的 `transform.x/y` 的 `fract()` 还原成绝对源坐标再交给后端。位置可能在
命令之后被 `CG[… X=…]` 改写,所以还原放在输出期而不是命令时刻。
