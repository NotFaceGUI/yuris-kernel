# DIV-RT-062 · 存档缩略图块布局随容器版本变化:0.479 必须 A=1536/+0x70,写 0.495 布局被官方拒收

- 状态: fixed(2026-11-20)
- 优先级: 高(内核写的 qsave/qload 官方读不了;官方 0.479 存档缩略图内核也读不出)
- 发现日期 / 发现方式: 2026-11-20 / 主人实机:两个 0.479 商业游戏
  (`黒獣2 ～淫欲に染まる背徳の都、再び～`、`聖奴隷学園2～完全調教版～`)
  qsave 后官方 QLOAD 无法读取;同一存档页缩略图/hover 异常。

## 复现

- 游戏位置 / 操作序列:
  - 0.479 商业游戏内 `QSAVE` → 本内核写 `save/save10001.sd`(容器版本
    0x138 正确)→ 关闭 → 官方 exe `QLOAD` 该槽 → 官方报错退出
    (0.479 LOAD 的 `0x1a64e`「File Check Error」路径);
  - 反向:官方 exe 写出的 `save00001.sd` 在本内核存档页显示缩略图失败。
- 锚点:存档 DNO=3(btype 1 图像块);`es_saveload.yst` 的
  `LOAD[FILE=… DNO=3 ID=_TMP_OF]`。

## 官方行为(真值层级 2 + 3)

官方 0.479 `聖奴隷学園２.exe`(sha256 `8e33d373…`)存档 LOAD
`FUN_00440490`:

- `0x4406ec`:`CMP version, 0x138`,不等即报「セーブデータのバージョンが
  異なります」(与 DIV-RT-058 一致);
- 图像块分支(`DAT_0065e523 != 0`):
  - `0x440894..0x44089d`:`CMP payload[0], 0x600`(1536),不等即
    `FUN_0045da94(0x1a64e,1)` → 读档失败;
  - `0x440a8f..0x440aa7`:宽 = 描述符 `+0x70`、高 = `+0x74`;
  - 随后按 `w*h*4` 建表面并复制 B 段像素。

真实存档对照(逐块解出后):

全系列 SDK(0.450–0.495,77 个官方包逐一下载 `yu-ris.exe` 扫描)只有
三套官方布局:

| 容器版本 | SDK 版本 | A 段 | w/h 偏移 | 证据 |
|---|---|---|---|---|
| `0x0C0` | 0.450–0.466(21 个版本) | **1520** | **+0x68** | 全系 exe LOAD 版本常量 0x0C0;0.459 `FUN_004382d0` @0x438f5f / 0.466 `FUN_00438b78` @0x43904a 硬校验 `A==0x5F0`,w/h 从描述符 +0x68/+0x6c 取 |
| `0x138` | 0.470–0.479(0.13) | **1536** | **+0x70** | 全系 exe 版本常量 0x138;0.479 `FUN_00440490` 0x440894 硬校验 `A==0x600`;样本 `アオリオ/save00001.sd`、`黒獣2/save00001.sd` |
| `0x1E0` | 0.479(0.14)–0.495 | **1600** | **+0x78** | 全系 exe 版本常量 0x1E0;0.495 `0x44734e`/`0x4477de` 硬校验 `A==0x640`;官方 `save00001.sd` 100×75 |
| `0x1E1` | 0.481 商业构建 | 1600 | +0x78 | `Erewhon` 官方存档 |
| `0x1E6` | 0.49x 商业变体 | 1600 | +0x78 | `光翼戦姫…/save10001.sd` |
| `0x1DA` / `0x1EF` | **非官方**(旧内核把 yscfg 版本误当容器版本) | 1600 | +0x78 | 仅为读旧档/覆写兼容保留;官方在版本检查处拒收 |

块类型 0 的 `var_id` 也随版本:0.479 官方写 **0**;0.495 写实际变量 id
(真实样本逐块对照)。LOAD 端不消费该字段,但写盘按版本对齐。

## 内核行为

`yu-save::image_block` 旧实现把写入端固定为 0.495 布局(A=1600、w/h
`+0x78`),读端试 `+0x78` 与错误的 `+0x68`:

- 0.479 官方 LOAD 硬校验 A==0x600 → 本内核写的 qsave 全部被拒;
- 0.479 官方存档的描述符 w/h 在 `+0x70`,读端两个候选都不命中 →
  缩略图解析失败(`sv.image.shape`),存档页该槽无法显示缩略图。

## 修法

1. `yu-save/src/profile.rs` 新增**版本档案表** `profile_for(version)`:
   每个已取证容器版本的写盘策略(图像块布局 + 块类型 0 的 var_id)
   集中在一处;`image_block::layout_for_container_version` 只做委托,
   不再维护第二份 match。
   - `0x0C0`(0.450–0.466)→ `LAYOUT_0466`(A=1520,w/h=+0x68);
   - `0x138`(0.470–0.479(0.13))→ `LAYOUT_0479`(A=1536,
     w/h=+0x70),var_id=0;
   - `0x1E0`(0.479(0.14)–0.495)→ `LAYOUT_0495`(A=1600,
     w/h=+0x78),var_id=实际值;
   - `0x1E1`(0.481 商业)/`0x1E6`(0.49x 商业)→ 同 0x1E0 布局;
   - `0x1DA/0x1EF` → 旧内核历史产物,兼容读取,新盘不主动选;
   - 其它 → `None`(未取证),跳过缩略图、不猜布局。
   **加新版本 = 在 `profile_for` 加一行 + 在 `profile::tests` 加一条断言**,
   生产代码不需要第二处改动。
2. `SaveState::flush` 只消费档案表:按本次写盘容器版本选布局/var_id。
3. `image_block::decode` 以 A 段长度做版本指纹(1536/1600),校验
   `w*h*4 == B 段长度`;旧 `+0x68` 候选删除(误读)。
4. `LOAD[ID]` 因此能读回官方 0.479 缩略图(不再只认 `+0x78`)。

### 读/写跨版本边界

- **读**:所有已取证布局自动识别(按 A 段长度 + B 段长度自证);未取证
  A 段长度显式报 `sv.image.shape`,不会按错误偏移解出畸形图。
- **写**:只写档案表里明确有布局的版本;未取证版本宁可缺缩略图也不写
  官方读不了的块。
- **容器版本本身**:启动时从官方 exe 的 LOAD 立即数探测、并从盘上 `.sd`
  学习(DIV-RT-058),不需要为新游戏手写;块压缩层(zlib/Snappy)同样
  按盘上存档/随包 DLL 学习。只有“图像块描述符布局”需要一行证据。

## 残余

- `0x0C0` 的块类型 0 `var_id` 政策没有官方存档样本(LOAD 不消费该字段,
  当前按实际 id 写);拿到 0.45x/0.46x 官方存档后补样本断言。
- 写盘描述符的未知字段仍为 0(官方 LOAD 只读 w/h 与 B 段);逐字节
  1:1 复原等取得完整描述符语义后另案。
- 0.450–0.495 全系列 SDK 已扫描完毕:官方只有 `0xC0`/`0x138`/`0x1E0`
  三套布局(商业变体 `0x1E1`/`0x1E6` 同 `0x1E0`),后续同代新版本
  不需要加表项。
