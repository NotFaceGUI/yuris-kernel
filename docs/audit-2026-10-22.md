## 1. A · 确定错误

### A1. 首帧 `COPY ID=:/W0/` 因主组直绘失去源（`offscreen_missing`）

- 证据（本次实测，`first_frame` tick 1）：

  ```text
  frame: 3   layers: 272 (visible 8)   passes: 14   offscreen passes: 1
  ops: 17 total, 12 drawn, 5 skipped
    skip copy  x1  gfx.copy.source.offscreen_missing      :/W0/CGS100
    skip image x1  gfx.imageop.copy_source.unsupported    :/W0/CGS100
  ```

- 机制：
  - J3 依据 EVID-J3-07 让 `build_group_passes` 跳过主组
    `:/W0`（`crates/yu-gfx/src/state.rs` 的 `if id == main { continue; }`）；
  - 但 `apply_copy_op`（soft）/`plan_group_compose`（wgpu）仍按
    “组必须有 Offscreen pass”去找源；
  - 首帧没有 `last_screen`（soft 回退到 `compose_group`，wgpu 回退到
    `group_image`），而主组已无 Offscreen pass ⇒ `offscreen_missing`。
- 影响：
  - `CGS100` 的 `COPY2 → RECTPAINT2` 链路在首帧必然失败；
  - golden `eris_first_screen_display.json` 仍把这条标
    `"status":{"executable":true}`，与运行结果不一致；
  - `cases/first-screen.json` 的 `ops_total=18` 与实测 17 对不上（见 C1）。
- 这不是“未取证”。主组直绘（J3）与 COPY 源（J2）两条已关闭的线之间
  没有接上：**主组成为“没有离屏纹理的组”后，COPY 需要一个明确的
  替代源**。两个候选（都符合现有证据，需择一）：
  1. 回退到“本帧主组子层的当前合成”（即临时按 `emit_children_ops` 画到
     一块临时表面，语义等于 J2 的 `compose_group`）；
  2. 官方 `COPY ID=:/W0/` 读的是**后缓冲**；首帧后缓冲尚不存在时，官方
     行为未取证 ⇒ 显式 `Unimplemented("gfx.copy.source.no_backbuffer")`
     并在报告里计数，**不能**报成 `offscreen_missing`（会把“未取证”
     伪装成“实现缺陷”）。
- 处置建议：在 `frame()` 里给主组 COPY 生成一个 `PassTarget::Texture`
  的自合成项（或让后端对“主组 + 无后缓冲”走专用回退）。在证据补齐前，
  至少把原因码改成 `gfx.copy.source.no_backbuffer` 并挂 DIV。

### A2. `image_probe_order` 空值仍有内置兜底（违反 A5 原文）

- `GfxState::from_tables`（`crates/yu-gfx/src/state.rs`）：
  - `probe_order_from_codes` 为空时**保留** `GfxConfig::new` 的默认
    `[png,bmp,jpg,gif,psb]`，只在帧诊断里加一条 `Info`。
- J4 把这条记成 `DIV-GFX-049 fixed`，但 `docs/architecture.md` A5 的原文是：
  > 缺表 = 显式拒绝启动或 `Unimplemented`，禁止内置兜底表。
- “记录一条 Info 后继续用默认表”正是内置兜底表。`yscfg` 是全工程必读的表，
  字段全 0 属于数据异常；此时继续跑会把“缺表”变成“看起来正常”。
- 处置：二选一（需主人裁决，两者都符合 A5）：
  1. `from_tables` 返回 `Err(gfx.config.probe_order_missing)`（拒绝启动）；
  2. 保留顺序但把**所有依赖探测序的层**标 `Unimplemented`，由后端跳过并计数
     ——不是只发一条 Info。
- 现状把它标 `fixed` 是**结论高于实现**。

### A3. `Engine::restart` 不重置渲染器状态（跨重启快照/后缓冲泄漏）

- `crates/yu-cli/src/engine.rs::restart` 只重置 `vm`/`state`/`timeline`/`frame`
  与报告字段，**保留** `Renderer`（`SoftRenderer`/`WgpuRenderer`）。
- 后果：
  - `SoftRenderer.last_screen` 与 `WgpuRenderer.backbuffer` 仍是重启前的
    屏幕内容 ⇒ 重启后第一帧的 `COPY ID=:/W0/` 会截到旧画面；
  - `SoftRenderer.snapshots` / wgpu `TargetSet` 的 snapshot 表不清空；
  - `GfxState.copy_seq` 从 0 重开 ⇒ 新 `CopyId` 会与旧快照 id 冲突，
    而 soft 的 `apply_copy_op` 有“`snapshots.contains_key(&copy.id)` 即冻结”
    的早退 ⇒ 新复制命中旧快照，**像素直接错**。
- K1 的 Restart 验收只比对了 title 稳定帧哈希（该帧 COPY 已结束），没有
  覆盖“重启后首帧含 COPY”的路径。
- 处置：给两个后端加 `reset()`（清 `last_screen`/`backbuffer`/`snapshots`/
  `image_cache`/`uploaded_overrides` 中与帧号无关的项），`restart` 调用；
  或用“重启代际”隔离 `CopyId`。二者都需要先定契约（快照是否跨重启保留）。

### A4. `REVERSE`/`HORIZONTAL` 的“源已加工”分支是死代码且语义可疑

- `crates/yu-backend-soft/src/render.rs::apply_image_op`：
  若 `st.texture_overrides` 含 `image.source`，就用覆盖纹理再加工。
- 但 `texture_overrides` 的键是**目标层**；`REVERSE`/`HORIZONTAL` 在 gfx
  只放行“无 ID2、原地”，所以 `source == target`，该分支在合法输入下
  只可能命中“同一层本帧已加工”的情况（例如先 `RECTPAINT` 再 `REVERSE`），
  这时它**跳过缓存**、直接基于当前像素做一次——这本身是对的，但：
  - 没有对应的测试；
  - wgpu 侧 `apply_image_to_override` 没有这个分支（两端行为可能不同）。
- 结论：不是“确定错误”，但属**未对拍的分支**。要么补两端一致的测试，
  要么删掉并把组合情况标 `Unimplemented`。

## 2. B · 文档失真

### B1. `dx_mode` 被写成“引擎双路径”，实际是内核自造契约

- 代码注释（`crates/yu-gfx/src/frame.rs`）已写明：
  > 官方引擎没有名为 `_DXMODE` 的渲染开关；该变量只改脚本分支。
- 但以下文档仍暗示引擎存在该路径：
  - `README.md`：“引擎着色器路径（`_DXMODE≠0`）未接”；
  - `PROGRESS.md` 成果 J4 §2/§4：“引擎双路径”“按 `_DXMODE` 选择”；
  - `docs/shader-parity.md` §6：“引擎侧没有渲染全局 `_DXMODE`”（这一句对）
    但同节标题与表格仍按“两条引擎路径”叙述。
- 事实链（`docs/shader-parity.md` §3 自身已给出）：
  - effect 始终创建；
  - psC 触发 = 有配对且 `TA>=1`；psD 触发 = 有配对且 `TA<1`；
  - `@_DXMODE` 只决定脚本走 `CGACT[TRANSITION]`/`TID` 还是 `DXBUF`。
- 因此 `CompositorFrame.dx_mode → psC/psD` 是**内核扩展**（默认 0 不改变
  现有行为），不是 1:1 对齐项。文档与 `dx_mode` 字段注释必须统一成
  “宿主/内核扩展；引擎无此渲染开关”。

### B2. README 的能力声明落后于实现

- `README.md` 模块表：
  - `yu-backend-wgpu` 行写“`_DXMODE` 待 J4；DIFFUSE 已按 J4 修复” ⇒ J4 已完成；
  - 同上“MODE 3/5/6/7/9 状态已有但后端未支持” ⇒ 两端已支持（`supported_blend`
    含这 5 个模式，`blend_table` 测试也断言可执行）；
  - `yu-gfx` 行仍把“5 个未对拍 MODE”与“11 个 shader 模式”并列，未区分
    “状态表已实现/像素未对拍”。

### B3. `render-parity` §12.6 与实现不符

- §12.6 写“`CGACT[COPY/COPY2/TEXCOPY/TEXSSCOPY]`：组目标复制仍
  `Unimplemented`”。实际 `CopySource::Group` 已实现（soft `compose_group`、
  wgpu `plan_group_compose`）；只有 `TEXCOPY/TEXSSCOPY` 仍是
  `gfx.copy.texcopy.unsupported`。
- §1 的 `CGACT` 行仍把 `SIZE` 归到“其余像素 Unimplemented”，但
  `SIZE/SIZE2` 已在 J3 实现（`scale_region`，两端共用）。
